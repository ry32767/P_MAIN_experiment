# IMU再有効化・無効ファイル削除、保存校正の再利用と毎回のカメラ動作

## 前提
- 2026-10-26 JST。ユーザーが保存済みIMU係数の再有効化と無効ファイルの削除を明示指示した。今回の削除は照合したK00002.CALだけを対象とする。実験ログや有効な校正、他のSDファイルは削除しない。
- 保存済みの個別校正/機体軸は再利用し、カメラ用は撮影と通常記録を開始後に毎回動作収録、実際の動画との時刻照合は撮影後のPC処理とする方式をユーザー確認済み。動作案内と検出を表示し、厳密にしすぎないとの指示を反映。
- 今回も親機とSpresenseだけに書込み。子機はUSB不足のためユーザー指示で未接続。子機のソースとビルド/ホスト試験まで。
- 親機USB A444A41EE9334705 / COM6とP_MAIN応答、Spresense USB 10878C89E6DBED1197F5F12D62C613AC / COM7とIMU_TIME/LINK/pps_input=D02応答を照合してから停止・更新した。
- ピン変更なし。GP6=GNSS PPS入力、GP7–D03=半二重、D02=PPS入力専用を維持。親機温度/水圧/LCDは対象外。元リポジトリ変更、PC Wi-Fi切替、実機Web自動試験、SDフォーマットなし。

## 実施と実測：IMUの再有効化
1. 親機XqとSpresense qの応答から双方の安全停止を確認した。
2. Spresense MainCore/loggerに明示USB保守コマンドを追加。停止済み・保存済み係数の形式/CRC/世代を確認し、有効状態の新世代を同期・読戻し後に適用する。起動時の自動削除は追加しない。
3. K00001.CALとK00002.CALを改めてUSB cで64byteずつ読み、ホスト側でCRC・形式・係数を検査。1番有効/2番無効、係数同一を確認し、PCへ両方の控えを保存した。
4. CAL ENABLE_SAVEDで係数を変えずK00003.CALへ有効状態を新規保存。3ファイルを再読出しし、1番/2番が元のまま、3番が同じ係数で有効であることを確認。
5. ユーザー指定の無効K00002.CALに対し、名前・CRC・世代・無効ビット・現在の有効係数との一致を検査して削除。再一覧でK00001.CAL/K00003.CALのみを確認し、1番と3番の内容保持を確認した。

|項目|結果|
|---|---|
|再有効化|generation=3、enabled=true|
|保持した有効ファイル|K00001.CAL、K00003.CAL|
|削除した無効ファイル|K00002.CALのみ|
|係数|元の有効1番と同一|
|削除前K00002.CAL SHA256|9851e2137ed2aa42de78993f7fe9d62ff2a12d947def0f3353b8fb72c496cd09|

実ログはrawのreenable_usb.txt、64byteの控えはbefore_/enabled_/after_*.CAL、要約はreenable_summary.json。削除対象の実験ログへの拡大や、未照合のファイルの一括削除は行っていない。

## 実施：保存校正の再利用
- SDから有効な個別校正を復元・適用でき、保存/復元エラーがなく参照番号も一致すれば、画面に「省略可」を表示する。存在だけ・無効レコードだけでは省略可にしない。
- 軸変換が有効なら「SDの軸合わせを再利用・カメラ動作のみ」を選べる。4姿勢を測り直さず、CAMERA_CAPTUREを新規作成して区間5だけを収録する。既存軸プロファイルと過去ログは保持する。
- 初回の機体軸合わせが未保存の場合は、4姿勢の測定/解析が一度必要。今回のIMU/磁気の保存・再有効化を、未実施の機体軸合わせの完了とは扱わない。
- 子機BNOはSDのDCD保存成功履歴を表示する。内部係数を直接読み戻して一致確認できたという意味にはしない。

## 実施：毎回必須の動作と案内
- 通常記録とカメラ撮影を先に開始し、約10秒ごとに「左右へ向きを変える」「機首を上げ下げ」「左右へ傾ける」を表示。30秒以上の経過とIMU更新/動きの検出を同じ箇所へ表示する。
- 確認は厳密な姿勢認定にしない。どれかのセンサ軸で0.08rad/sを超える動きを1秒以上離れた時刻で検出し、更新が新しければよい。全軸検出・指定角度/順序への一致は要求しない。開始後3秒は古い応答を除き、5秒以上の更新途絶は区間終了不可。実際の相関品質は後処理で確認する。
- 今回の完了は起動/通常ログ/個別校正参照に結び付け、RAMだけに保持。新しい記録準備・再起動・SD再認識等で解除する。古いカメラ変換やSD保存では代用できない。
- 測距開始/test/明示承知API/USB T、実際の親機送信・子機受信に必須ガードを追加。未対応子機のCAMERA_READY未設定も未完了として扱う。個別校正・軸校正の警告の明示承知ではカメラ動作を迂回できない。
- カメラ専用ログから--movement-onlyで動作CSVと収録情報を取り出し、--capture-infoでカメラ時刻を照合できる。軸の再測定/再インポートは不要。動作CSVのSHA256と収録情報も照合する。
- カメラの新しい撮影開始は本機から自動検出できない。撮影切替時は新しい実験準備から始めることを案内する。MP4直接抽出・カメラ時計設定・自動撮影開始は含まない。

## 検証
- 指定のホスト試験を通過。実際のUSB保守関数を偽SDへ接続し、停止条件・有効ファイル拒否・CRC/パス/係数/競合ガードを確認。
- 実SD保存実装の試験でカメラ専用収録のmask16、保存軸の保持、30秒/動き/更新条件、再起動後の完了非流用、104byte状態上限を確認。
- 親機のSpresense CSV/子機のIMU binからカメラ専用収録を解析し、新たな軸校正として誤使用しないことを確認。既存の任意回転復元・CRC破損・カメラ相関/中間不整合拒否の試験も通過。
- 実画面処理で省略モード、10秒ごとの指示、終了可否、カメラ未収録の測距拒否を試験。実APIガードを抽出し、片方だけ完了では進まないことを確認。
- localhost模擬画面をデスクトップと375px幅で確認。動作指示と検出表示の画像はmotion_guidance.png/motion_mobile.png。実機Webを確認したことにはしない。
- parent/child100、Spresense formatter/loggerをビルド。今回のSpresense変更はMainCoreのみを書込み、SubCoreのABIと処理は維持。

親機更新後にIMU補正有効3番・磁気補正有効1番へ校正セットの参照を合わせ、親機セット3番として新規保存・一致を確認した。最初の保存要求はSpresenseの処理中ガードで拒否され、処理完了/保存可能を確認してから保存した。USB Tは今回の動作未収録として実機で拒否され、測距停止を維持した。

Spresenseを安全停止してから親機経由のRESETを要求。要求受付後、起動後のcalibration=0/last_operation=0、generation=3/applied=true、復元エラー0、通常記録の再開、親機セット一致を27個の新しい応答で確認した。これによりSDからの再起動復元も確認した。restore_boot.txt/restore_boot_summary.jsonを参照。

最終の約18秒では親機保存件数545→563、Spresense 109909→125754、双方記録中・当該窓の新規SDエラー0、GPS/PPS時刻源・Spresense PPS対応成立、Web待受けtrue、配備ハッシュ一致を確認。機体軸プロファイルは未保存g=0、今回の動作も未収録k=0であり、測定済みを捏造していない。最終結果はrawのfinal_summary.json、応答はfinal_after.txt/json、セット保存/USB拒否はparent_finish.txtを参照。

再起動前にはSpresenseでWRITE/errno110の一時エラー2件と自動復旧1回を観測した。保存要求/再開要求が受付状態のまま待つ窓もあり、再照会・再開後に件数増加を確認している。sd_recovered_window.jsonとparent_resume_retry.txt/jsonを保存。再起動で累積カウンタが0へ戻っても、この履歴は解消済みの精度/安定性合格とはしない。原因と長時間安定性は未調査。

- 動画とIMUの対応・取得遅延・同期/姿勢/距離精度・長時間/温度/磁気外乱下の安定性は未測定。

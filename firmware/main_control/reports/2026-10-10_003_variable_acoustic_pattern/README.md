# 毎回変わる音響パターンとテザー照合

日付: 2026-10-10

## 前提

ユーザー依頼: 測距ごとに音響パターンを変更し、テザーで通知したパターンと照合して前回などの遅延マルチパスを区別する。Pico 2 W / Arduino-Pico / PlatformIO、既存配線。ピン変更・隣接元リポジトリ変更・実機書込み・Wi-Fi切替・既存ログ削除／フォーマットなし。Spresense・親機温度／水圧／LCDは今回の検証対象外。

## 実施

3バースト（各5波）の休止を1.0〜5.2ms、7.0〜11.2msの各8段階、600µs刻みで64種類にした。IDは17ずつ進め、一巡するまで重複しない。予約成功時にのみ消費し、同一起動中は予定送信時刻で同じIDの再使用を16秒以上空ける。設定変更や送信の停止・再開で履歴をリセットしない。再起動では履歴は消える。

通信v5・163 byte。CRC付きSCHEDULEに測距番号・ID・両休止時間を追加し、子機で表との整合性を検査。受信は通知された2間隔だけを照合。RESULTでも同じ情報を返し、親機は予約との不一致を取得異常にする。既定モードを可変3連に変更し、送信OFFは維持。コンソールにモードと直近IDを表示。HEALTH/SHOTログ・PC読出し・README/specを更新。

## ソフトウェア検証

- ホストテスト成功（既存P_MAIN_experiment/.venvのPython）。64種類×64種類×4周波数の16384組で、別パターン単独の不採用を確認。
- 非重畳の旧パターン後に今回のパターンが届く条件、22ms窓末尾、±200µs境界／±201µs拒否、欠落・ノイズ・候補溢れを確認。
- ID一巡・再使用16秒の境界・不正ID／休止時間、予約とRESULTのメタデータ不一致を確認。
- バイナリ新フィールドと旧2種類の長さ、CRC、オフライン画面操作・構文を検証。
- 親機／child100／child50をビルド。

生出力はreports/raw/2026-10-10_variable_pattern_{host,build,ui,console}.txt。

計算: 163 byte / 115200bpsで14150µs。最長パターン確認延長18150µs（10kHz）。予定RESULT期限のモデルは2フレーム＋3ms応答待ち＋100ms予約余裕＋22ms窓＋18150µs確認＋50ms期限＝221450µs。4回/秒の250000µs枠に収まるが実機遅延は含めない。

## 実測・未検証

実機測定は実施していない。反射低減効果・距離精度・受信成功率・実送信周期・PIO波形・比較器の応答・SD負荷は未検証。今回の信号自身の反射、16秒より遅い同一IDの反射、再起動を跨ぐ反射、複数の反射が重畳して期待間隔が偶然成立する場合を排除できる保証はない。比較器エッジの観測記録はパターン確定後に開始するため、最初の2バーストの全エッジ保存を保証しない。ADC包絡線は従来どおり事前に準備する。

## 実機確認手順

USB個体番号と役割応答を両方確認してから親子を更新。ユーザーが親機画面で観測記録を無効、可変3連、1回/秒→4回/秒を試す。ID変更とSHOTログ、遅延した旧パターンの拒否、直達波と反射条件での受信率を確認する。設定適用後は明示的に送信開始。既知距離／波形実測で許容幅を評価する。PCのWi-Fiは切り替えない。

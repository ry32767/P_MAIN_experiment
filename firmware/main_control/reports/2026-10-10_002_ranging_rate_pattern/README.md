# 測距回数と簡易3連音響パターン

日付: 2026-10-10

## 前提

Pico 2 W / Arduino-Pico / PlatformIO。既存の音響TX/RX・RS485配線を前提とする。ピン変更なし。隣接AquaBeaconは読取照合のみ。Wi-Fi切替・実機書込み・SD既存ログ削除／フォーマットは行っていない。親機温度／水圧／LCDは対象外。

## 実施

- コンソールに1〜4回/秒と単発／3連（各5波、約1ms/2ms休止）を追加。
- 子機で3連の間隔照合、64候補上限と溢れ検出、最初の到来時刻でToF計算。
- 測距トランザクション・操作通信を排他化。UTCを空き時間へ配置。遅延枠を連射しない。
- 通信v4・158 byte、ログ末尾のrate/patternと旧長さ読出し対応。仕様・README同時更新。

## ソフトウェア検証

親機・child100・child50のPlatformIOビルド成功。ホストテストは通常pythonにziglangがなかったため、既存P_MAIN_experiment/.venvのPythonで実施し成功。設定境界、パターン成立／欠落／間隔不一致／ノイズ／22ms境界／候補溢れ、測距中・問い合わせ中・操作中の新規枠抑止、CRC、バイナリ旧長さ互換を確認。オフラインWeb構文・設定操作・5タブ・ラベルのテスト成功。

child50の生出力: ../raw/2026-10-10_rate_pattern_child50.txt。

生出力: ../raw/2026-10-10_rate_pattern_build.txt / rate_pattern_host.txt / rate_pattern_ui.txt / rate_pattern_console.txt（後3件も2026-10-10_接頭辞）。

モデル上、158 byteは13716µs、最悪の予定RESULT期限は207182µsで4回/秒の250000µsより短い。これはフレーム転送時間・3ms待ち・100ms予約余裕・22ms窓・4750µsパターン確認・50ms期限の計算で、実機の処理遅延／周期実測ではない。

## 実測・未検証

実機の測定は行っていない。距離精度、送信回数、反射低減効果、PIO実波形、比較器包絡線の伸長、RS485方向切替、SD負荷、消費電力は未検証。反射も同じパターンを持つため、直達波不検出時の反射誤採用は残る。3連の比較器ログはパターン確定後に開始され、最初の2バーストの全エッジを保存する保証はない（事前ADC包絡線は取得を準備する）。

## 実機での確認手順

USBシリアル番号と役割応答で親子を識別してから、両方を更新する。ユーザーが親機Webの実験タブで観測記録を無効、2回/秒・単発→4回/秒・単発→3連を順に試す。設定適用後は明示的に送信開始する。既知距離で受信率・誤検出・波形・実送信周期を確認し、反射条件を変えて比較する。操作中の休止／終了後再開も確認する。PCのWi-Fiは切り替えない。

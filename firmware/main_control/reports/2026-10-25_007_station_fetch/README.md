# Fetch Aborted・保存済みテザリング接続の修正

## 前提
- 基準局一覧操作でFetch Aborted。途中でユーザーは「Web画面は開くが親機がテザリングにつながらない」と補足。保存済み設定で接続する操作も確認。
- PC Wi-Fiは切替えない。実機Web操作はユーザーが担当。SDフォーマット・既存ログ削除なし。親機温度・水圧・LCD、ピン変更は対象外。
- COM6/USB番号A444A41EE9334705とP_MAIN応答を照合。書込みはscripts/flash.pyによるX/q安全停止・再識別後に実施。

## 調査結果
- 初回USBではAP起動・Web待受あり、テザリング側IP未設定・未接続。Webの要求48件/完送48件、タイムアウト0。これだけで報告時のFetch Abortedの唯一の原因とは断定しない。
- 同じWi-Fi情報を再適用した場合に、未接続でも再試行を省略する前回修正の不具合を発見。
- ブラウザーの操作期限5秒に対し、親機の空HTTP接続保持が7秒あり、後続要求が期限を超えて待たされ得る。
- 導入済Arduino-PicoはbeginNoBlockでも内部CYW43::beginが接続完了を待つ。既定_timeoutは15000msで、その後に期限なしの交渉待ちもあった。WebとSD処理が止まる経路であり、前回の非同期APIという想定は不十分だった。
- 中間版の起動後にUSBで保存設定の自動復元とテザリング接続を確認。sta_ip=172.20.10.4、wifi_configured=true、wifi_attempts=1、mode=3、AP起動/待受true。AP直接接続端末0台。
- ユーザーが172.20.10.4で「基準局一覧を受け付けました」の応答を確認。受付と取得完了を区別。
- その後のUSBではWi-Fi接続済みだが補正サーバー接続失敗、table_ready=false、対応局0件。PCの通常回線では同ホスト/2101からSOURCETABLE 200 OKを確認（DNS34ms、DNS開始からTCP接続まで55ms）。PCの結果をスマホ回線の合格とは扱わない。

## 変更
- 保存設定読込み・設定再適用時、未接続なら同一Wi-Fi情報でも再試行。未接続時はHTTP処理の合間に30秒ごとに再試行。接続済みなら再接続しない。
- ボタン名を「SDの設定を読み込んでテザリングへ接続」に変更。設定の有無、接続状態、試行回数を画面/USBへ表示。
- 基準局操作でWi-Fi名が未設定なら案内。未接続の有効な開始操作では再接続を予約し、Web受付応答完送後にNTRIP処理を開始。
- 操作重複を抑止。中断時は受付状態が不明なことを日本語で表示。要求データのないHTTP接続を1秒で解放し、受信途中・送信中の期限は維持。
- lib/lwIP_CYW43へ導入済ライブラリをコピーし、STAのjoin要求受付で戻る変更を局所適用。既存著作権/LGPL表示を保持。共有frameworkと隣接リポジトリは変更しない。AP・フレーム送受信経路は元のまま。
- NTRIP DNSは永続バッファ/世代付きコールバックで非同期化（5秒期限）。遅延した旧コールバックを破棄。TCPはIPで接続し待ち上限を200msから2秒へ変更、ストリーム送信は200msへ戻す。DNS失敗とTCP失敗を分離。画面の状態取得期限を5秒へ変更。
- README.mdとdocs/spec.mdへ追記。新規docsなし。

## 未検証・制限
- RTK補正の実受信、長時間のAP+STA継続、APチャネル変更時の再接続挙動。
- TCP接続試行には最大2秒の処理待ちが残る。初期無線設定の低水準呼出しやチャネル移動の瞬断まで無停止とは断定しない。
- 保存設定の最終版での物理電源断保持、時刻・距離・位置精度は未検証。

## 操作
1. スマホのテザリングをON。
2. 初回SD認識で保存値を自動復元する。画面から明示する場合は「SDの設定を読み込んでテザリングへ接続」。入力し直す必要はない。
3. テザリング元スマホではUSB W/時刻・位置のSTA IPを使う。観測時は http://172.20.10.4/ 。IPは再割当てで変わる場合がある。192.168.4.1はAquaBeacon-MAINへの直接接続用。
4. 更新後はページを再読み込みして「基準局一覧を取得」。受付表示だけでは完了ではない。状態が「基準局一覧取得済み」となり選択欄が埋まることを確認。

生ログ・変更前ソース・PC外部キャスター照会・ビルド・試験・書込み：reports/raw/2026-10-25_007_station_fetch/。

## 最終実機での追加切り分け
- 非同期STA初期化後は、join前にLINK_UPを解除する。認証前のDHCP送信を避け、実際の無線link-upイベントでDHCPを進める。ホスト試験でもjoin時点のリンクdownを確認。
- 修正後USBでは保存設定あり・試行1回でテザリング接続true、172.20.10.4を確認。
- さらに、AP先行起動でAP自身のgatewayがdefault routeを占有し、通常のcheck_routeが既定経路を置換しないことをソースで確認。CYW43lwIP::beginでSTAを_default=true、APをfalseに設定し、STAのDHCP成立時に外向き経路をSTAへ切替える。直接APのサブネット内通信は通常の経路選択を使う。
- ユーザーは中間版で受付表示まで確認したが、取得完了は確認できず。受付を成功扱いしない。

## 既定経路修正版の起動後実測

- 保存済み設定あり、試行1回でテザリング接続true、172.20.10.4、mode=3、AP起動true、Web待受trueを確認。
- ユーザー側からのWeb画面1回完送・状態取得33回、HTTP受付40/応答完送40、タイムアウト0をUSBで観測。テザリング接続とスマホWeb通信の同時継続をこの観測区間で確認。長時間安定性とは区別。
- この時点ではRTK操作停止中で、基準局一覧完了は未確認。ユーザーに最新版での一覧取得操作を依頼。

- ユーザーがテザリング元スマホのWeb操作で基準局一覧の表示を確認。
